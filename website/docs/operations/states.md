# Node states

`getStatus` reports `state` and `stateName`. The state is persisted in `config.json` as `GlobalState` and drives what the signer does.

| Value | State | Meaning | What the signer does |
| --- | --- | --- | --- |
| `0` | `LiveState` | Normal operation | Alternates wrap and unwrap signing ceremonies on the momentum window, sends signatures, syncs both chains |
| `1` | `KeyGenState` | The bridge's `allowKeyGen` flag is set | Waits for the key-gen window, runs the TSS key generation with the other Pillars, then returns to live |
| `2` | `HaltedState` | The bridge is halted on Zenon or an EVM chain | Signs nothing; polls until the halt is lifted and the unhalt duration has passed |
| `3` | `EmergencyState` | This signer observed a redeem registration on one network (an EVM `RegisteredRedeem` or a NoM unwrap request) with no matching request on the source network | Signs halt messages with the other signers, submits them when selected, and moves to halted |
| `4` | `ReSignState` | The bridge administrator activated a re-sign for one network through bridge metadata | Walks every wrap request for that network, re-signs the ones whose signatures are no longer valid, then returns to live |

The flags and parameters behind these transitions are described in [Bridge parameters](../bridge-parameters.md), and the halting design in [Security model](../security-model.md).

The administrator can halt a network unilaterally. Ordinary signers halt only through the threshold-signed emergency ceremony, and reach `HaltedState` when the bridge's halt flags are set, however they were set.

A halt or key change is signed for the EVM networks the bridge lists when the messages are built, and each signature is sent only to the network it was signed for. A network the bridge removes in the meantime needs nothing more. If the bridge adds a network during the halt, the signer signs the halt again for every network it lists; a key change has no signature for the added network, so the signer still sends it to the networks it was signed for and completes once they hold the new key. If the added network does not already hold the new key, the signer logs an error naming it, and that network keeps the key it holds.

The signer also asks to be restarted, rather than continuing, when a subscription or storage operation fails in a way it cannot recover from. Run it under a supervisor with automatic restart.

## The bridge-account listener

The listener reads the bridge contract's account blocks in order and stops at the first one it cannot process: a block the Zenon node has not confirmed, a node that reports it is still syncing, or an unwrap request whose source event the EVM endpoint cannot be asked about. It retries every four seconds and reads nothing after that height in the meantime, including a halt. The hold is visible as `zenon.receiveHold` in the [health snapshot](../health-api.md) and, after a minute, as an error line that repeats every minute. After ten minutes at the same height a signer that is signing transfers stops rather than keep signing without its listener; a signer in `EmergencyState` or `HaltedState` keeps retrying. A supervisor restart retries the same block during startup; [A held startup](#a-held-startup) says when that start exits again and when it stays up.

Once a signer's database has followed the bridge account to its tip, or has met a receive that it had to check on the way there, it keeps a record that it vouches for the account. From then on the signer checks the source event of every unwrap request it reads from then on, whenever it reads it: live, after a hold, or after a restart. An endpoint with no receipt for a request's transaction settles the question only while the receive is still within finality. Read later, the signer looks for the event in the block its own scan of the source chain recorded, and if it has no such record it holds the request and reports it instead of judging it: the transaction may never have existed, or may lie outside the endpoint's history. Following a long stop or a [checkpoint restore](sync-checkpoints.md), start it against EVM endpoints that still serve the receipts and logs for the period it was away.

## A held startup

At startup the signer reads the bridge account from its checkpoint to the tip, then scans each EVM network from its cursor to the head, and only then begins to sign. A receive it cannot process during that first read ends the process, and the supervisor restarts it.

Two cases keep the process running instead, with the read retried every four seconds:

- **The request waits for this signer's own record of the source event.** The EVM endpoint has no receipt for the request's transaction, and the block this signer's scan recorded for the event is missing, for a receive read after finality, or cannot be read from the source chain. The EVM scan, or a [backfill](backfill.md) requested on this start, is what writes that record, so the EVM networks start while the read is held.
- **The signer is in `EmergencyState` or `HaltedState`.** It signs no transfer in either state and has the halt to sign or to keep, so a receive that fails does not end its start. Such a signer also begins the halt ceremony without waiting for the EVM scans.

While startup is held, `phase` in the [health snapshot](../health-api.md) stays `syncingBridge`. `zenon.receiveHold` shows the height while the read of the bridge account is held; it is `null` once that read has reached the tip and startup waits only for the EVM scans or the halt flags. The signer signs and sends nothing for a wrap or an unwrap, generates no key and re-signs nothing. In `EmergencyState` it signs and submits the halt, and in `HaltedState` it watches the halt. The held receive keeps its place: its checkpoint is written only once the receive has been processed, source check included. Startup is complete, and `phase` becomes `running`, when the bridge account has been read to its tip, every EVM network has finished its startup scan, and the bridge's halt flags have been read.

A held start ends the way a hold of the running listener does: after ten minutes at one height a signer outside `EmergencyState` and `HaltedState` stops. Time during which the EVM startup scans are still running does not count, so a long scan or backfill is not cut short. If the scans finish and the request is still held, the log line names the cause. An event in a block that is not yet final on the EVM chain is still in the confirmation queue, and its block is recorded when it confirms. An endpoint that fails or disagrees about a block this signer already recorded keeps the request held until it answers. If neither applies and the signer's EVM cursor was already past the event's block before this start, the scan did not cover it: restart with a backfill that reaches that block, or follow the "cannot be judged" row in [Troubleshooting](troubleshooting.md). Each EVM network starts on its own, so a network whose node is still syncing does not keep the others from scanning; startup completes once every one of them has. An EVM network that fails to start beside a held startup stops a signer that is signing transfers, as a failed start always has; a signer in `EmergencyState` or `HaltedState` starts it again every 30 seconds.

A start reads a bridge account block that is already final as history, a held start included: what the block changed is taken from the networks, token pairs, administrator, signing key, settings and halt state the signer read from the bridge when it started. A retry of a held start can read a change that was made after that. It then reads no further block and does not complete, because the next block would be judged with what the signer read before the change. The signer stops at once, and its next start reads the bridge as it is then. The exception is a signer in `EmergencyState`, which is not stopped while it has the halt to sign, since a restart could cost it the key it has loaded. It keeps running on the networks and settings it loaded, fixes no affiliate settings for new unwrap events, and stops once it has signed the halt for the networks it knows and left `EmergencyState`. If the change added or removed a network, the halt messages this signer builds differ from those of signers that know the new list, so it takes no part in their ceremony until it has restarted; restart it by hand if the halt depends on it. Its next start, in `HaltedState`, looks at every network the bridge lists then, and returns to `EmergencyState` if one of them is not halted. The same holds for a start that had already read such a change as history before the receive it failed on: it exits as every failed start does, except in `EmergencyState`, where the signer is kept and reads no further.

Every start looks at the bridge's halt flags before startup completes, after the signer has applied the bridge's metadata, and moves a signer in `LiveState`, `KeyGenState` or `ReSignState` to `HaltedState` if the bridge is halted on Zenon or on any EVM network it lists, as the listener does when it reads a halt. A network the bridge adds while the flags are read is looked at before startup completes. A start that waited for the EVM scans exits if the flags cannot be read. A start that returned before startup was complete does not complete it then, and reads the flags again every 30 seconds; the log line names Zenon or the chain id of the EVM network whose flag could not be read.

A database reading the bridge account for the first time has no such record yet. There the signer checks a receive that is still within finality and a request the bridge still withholds, one inside its redeem delay, in the same way. It records a request that is past its delay, redeemed or revoked without looking up its source, because the transaction may be older than the endpoint's history.
